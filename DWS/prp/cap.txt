🏗️ La Arquitectura que quiere tu profesor (El plano)
Capa 1: Vista (Frontend): HTML (estructura), CSS (estilos), JS (interacción). Envía peticiones HTTP (JSON/HTML).

Capa 2: Servidor (Backend): PHP. Recibe peticiones, aplica lógica de negocio, validaciones, seguridad, y se comunica con la BD mediante Procedimientos Almacenados (SP).

Capa 3: Base de Datos (MySQL): Almacena datos y ejecuta los SP (que contienen lógica, validaciones y seguridad).

🎯 Backend: Lo que SUMA y lo que RESTA puntos
1. Estructura del BackEnd (20%)
✅ SUMA (Excelente): Separar responsabilidades en carpetas/archivos claros: config/ (conexión), controllers/ (lógica), services/ (reglas de negocio), models/ o repositories/ (acceso a datos), procedures/ (llamadas a SP) y errors/ (gestión de errores).

❌ RESTA (Deficiente): Tener todo el código PHP en un solo archivo, mezclar consultas SQL con HTML, o no tener una estructura definida para Login y Registro.

2. Lógica de Negocio PHP (20%)
✅ SUMA: Validar todos los datos de entrada, usar password_hash() para las contraseñas, manejar excepciones con try/catch, y enviar la contraseña ya hasheada al Procedimiento Almacenado.

❌ RESTA: No validar campos, guardar contraseñas en texto plano, o que el código PHP sea un desastre que no permita reutilizar funciones.

3. Acceso Limpio a MySQL (20%)
✅ SUMA: Usar PDO con prepared statements (para evitar inyección SQL), abrir la conexión solo cuando se necesita y cerrarla al terminar. Comunicar errores claros a PHP.

❌ RESTA: Usar mysqli con concatenación de strings (peligro de inyección SQL), dejar conexiones abiertas, o no capturar los errores de la base de datos.

4. Calidad de Procedimientos Almacenados (20%) — Ojo aquí, es clave
✅ SUMA: El SP de Login/Registro debe validar datos internamente, controlar errores mediante parámetros de salida (ej. OUT mensaje_error), y aplicar lógica de negocio. No debe ser solo un INSERT o SELECT disfrazado.

❌ RESTA: SP que solo encapsulan un CRUD, que no validan nada, o que no devuelven un código de error/éxito claro.

5. Integración con FrontEnd (20%)
✅ SUMA: El backend debe devolver respuestas claras (JSON con status, message, data), y los errores deben ser fáciles de mostrar en el frontend. Login y Registro deben funcionar de forma completa.

❌ RESTA: Devolver HTML crudo en lugar de JSON, errores 500 sin mensaje, o que el frontend tenga que adivinar qué pasó.

🎨 Frontend: Lo que SUMA y lo que RESTA puntos
1. Estructura semántica HTML (20%)
✅ SUMA: Usar <header>, <main>, <section>, <form>, <label>, <input>, <button>. Accesibilidad (atributos aria-*, alt). Estructura clara para Login y Registro.

❌ RESTA: Usar <div> para todo, no asociar <label> con <input>, o una estructura que no se entienda.

2. Funcionalidad JavaScript (20%)
✅ SUMA: Validar formularios en el cliente antes de enviar (campos vacíos, formato de email, contraseñas seguras), gestionar eventos (click, submit) y mostrar feedback en tiempo real.

❌ RESTA: No validar nada, que el formulario recargue la página sin control, o que los botones no hagan nada.

3. Navegación entre vistas (20%)
✅ SUMA: Transiciones fluidas entre Login y Registro. Puede ser MPA (multipágina) o SPA (Single Page Application) bien organizada. Enlaces claros.

❌ RESTA: Enlaces rotos, navegación confusa, o que el usuario tenga que escribir la URL manualmente para cambiar de vista.

4. Diseño visual y maquetación (20%)
✅ SUMA: Estética coherente con un videoclub (colores, tipografía, iconos). Maquetación cuidada con Flexbox/Grid. Posicionamiento preciso de formularios, botones y paneles.

❌ RESTA: Diseño desordenado, elementos superpuestos, colores ilegibles, o que no parezca un videoclub.

5. Experiencia de usuario (20%)
✅ SUMA: Mensajes de error claros (ej. "El usuario ya existe", "Contraseña incorrecta"), transiciones suaves, controles comprensibles. El personal de Sakila debe poder usarlo sin manual.

❌ RESTA: Mensajes genéricos ("Error"), movimientos bruscos, o que el usuario no sepa qué está pasando.

🚀 Resumen del "Viaje del Dato" que debes implementar
Usuario interactúa en la Vista (HTML/CSS/JS).

JS valida y envía petición HTTP (JSON) al PHP.

PHP recibe, valida, hashea la contraseña y llama a un Procedimiento Almacenado en MySQL.

MySQL ejecuta el SP (que valida, controla errores con parámetros de salida, y devuelve datos).

PHP recibe el resultado, lo formatea en JSON y lo envía de vuelta.

JS recibe la respuesta, actualiza la vista (éxito o error) sin recargar la página (o con recarga controlada).

💡 Consejo final de experto:
Si quieres asegurar el 4/4 en Calidad de Procedimientos Almacenados, asegúrate de que tus SP tengan:

IN para los datos de entrada.

OUT para códigos de error y mensajes.

DECLARE EXIT HANDLER FOR SQLEXCEPTION para capturar errores.

Lógica de validación interna (ej. verificar si el email ya existe antes de insertar).
